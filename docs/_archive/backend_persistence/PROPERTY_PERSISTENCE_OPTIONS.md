# 属性保存与恢复方案

## 1. 目标

围绕后端对象属性（`PropertyBag`、可编辑属性、组件属性）建立稳定的保存与恢复机制，满足：

- 保存后可完整恢复对象业务状态
- 属性系统与 UI 属性面板解耦
- 支持后续属性扩展与版本演进

## 2. 方案对比

## 方案A：`PropertyBag` 全量快照（推荐）

### 保存

- 每个对象写入：
  - `propertyBag`: `PropertyBag::toJson()` 全量结果
  - `components[*].data`: 组件自身属性（如 follow）
- 几何/位姿等核心字段继续独立保存，不与 `propertyBag` 混写

### 恢复

1. 先恢复对象核心字段（id/class/pose/rotation/color）
2. 回填 `propertyBag`
3. 按 key 调用必要同步钩子（如姿态相关、follow 相关）
4. 再执行组件恢复与后处理

### 优点

- 改造小，和当前 `BackendDataBase` 结构最贴合
- 扩展属性时无需频繁改 `MainWindowProjectIo`
- 可作为“对象状态真源”，避免 UI 快照驱动

### 风险

- 缺少强约束，历史脏 key 可能累积
- 跨版本 key 重命名需要迁移策略

---

## 方案B：强类型属性 Schema（严格模型）

### 保存

- 不保存通用 `propertyBag`，只保存明确定义字段：
  - `transform.*`
  - `display.*`
  - `simulation.*`
  - `custom.*`（受控扩展）

### 恢复

- 按 schema 严格校验，缺字段走默认值，非法字段忽略并告警

### 优点

- 数据质量高，长期可维护性强
- 版本迁移规则明确，测试更容易覆盖

### 风险

- 初始改造成本高
- 每新增属性都要更新 schema 与迁移逻辑

---

## 方案C：双轨制（核心强类型 + 扩展 bag）

### 保存

- 核心属性：强类型字段（`transform/display`）
- 扩展属性：`propertyBag.custom`（或 `extensions`）

### 恢复

- 先恢复强类型核心属性
- 再恢复扩展 bag
- 冲突时以强类型字段为准

### 优点

- 稳定性与灵活性平衡
- 适合逐步从历史数据迁移

### 风险

- 需要定义冲突优先级与去重规则

## 3. 推荐选择

结合当前 CloudSim 代码现状，建议采用 **方案C（双轨制）**：

- 短期先按方案A快速落地（最小改动）
- 同步引入核心字段白名单（向方案C演进）
- 后续再逐步把关键业务属性迁到强类型字段

## 4. 恢复顺序建议（关键）

固定顺序避免状态互相覆盖：

1. 创建对象并恢复核心字段
2. 恢复 `propertyBag`（仅数据）
3. 恢复组件（可能覆盖部分关联属性）
4. 执行属性同步钩子（姿态、跟随、可见性）
5. 执行 `follow solve` 与场景同步
6. 最后刷新属性面板

## 5. 版本与迁移策略

- `version=4` 起引入 `propertyBag` 正式字段
- 提供 `migrations[]`：
  - key 重命名
  - 类型转换（string -> number）
  - 废弃 key 清理
- 加载时记录迁移日志，写入 `RunInfoPage`

## 6. 验收标准

- 同一工程保存-恢复后，关键属性键值一致
- 属性面板显示值与后端对象实际值一致
- Follow/姿态/颜色等关键属性恢复后行为一致
- 新增属性不修改主流程即可保存恢复
